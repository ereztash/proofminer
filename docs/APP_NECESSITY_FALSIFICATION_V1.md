# ProofMiner — App Necessity Falsification v1

Date: 2026-08-16

## Hypothesis under attack

> A suitable user needs a ProofMiner application in order to receive the value of safer professional commitments.

This hypothesis has **no default right to survive**.

The system must distinguish:

- **user need** — a costly commitment is about to be made under uncertainty;
- **capability** — preserve the before-state, expose load-bearing assumptions, discriminate evidence, link outcome;
- **delivery surface** — app, extension, plugin, inline card, API, workflow, human service, or none.

The delivery surface is subordinate.

---

# Adversarial attacks

## A1 — Destination-app attack

If the user must remember to open ProofMiner, reconstruct context and then return to work, the app creates a new task exactly when the user is trying to complete an existing one.

**Kill:** if equivalent support can be invoked inline with less context switching, the standalone app loses the primary surface.

## A2 — General-AI substitute attack

A capable general AI with connected work data, project memory and a short decision protocol may reproduce most reasoning primitives cheaply.

**Kill:** if ProofMiner's output is mainly better prompting / structured reflection, there is no product moat.

## A3 — Workflow-platform attack

Existing work platforms increasingly support event-triggered agents and workflows inside the surfaces where commitments form.

**Kill:** placement is not sufficient differentiation. ProofMiner must contribute a decision-specific state model / evidence loop that the host platform does not cheaply recreate.

## A4 — Interruption-cost attack

The product asks for cognitive control precisely at a moment when the user is already acting. Every intervention creates a switching and resumption cost.

**Kill:** if intervention burden is comparable to or larger than expected decision value, the correct behavior is silence or no product.

## A5 — Commitment-detection attack

Many consequential commitments are not discrete. They emerge through gradual scope creep, repeated small allocations, conversations and path dependence.

**Kill:** if no reliable observable trigger exists in one bounded work surface, an automatic safety layer cannot claim dependable presence.

## A6 — Context-completeness attack

A calendar event, task or proposal rarely contains the full rationale, evidence, constraints and history needed to judge strategic materiality.

**Kill:** if the system needs broad cross-tool surveillance to achieve useful context, permission/privacy/integration burden may exceed the value.

## A7 — Sparse-learning attack

Major professional-transition decisions may be infrequent, heterogeneous and slow to yield attributable outcomes.

**Kill:** if repeated comparable commitment cycles are too sparse, the Decision Flight Recorder cannot compound fast enough to create defensibility.

## A8 — Outcome-attribution attack

A later success or failure rarely identifies which assumption or decision caused the outcome.

**Kill:** lineage cannot upgrade itself into causal learning merely because an outcome is linked to a prior decision.

## A9 — Safety-over-action attack

The user may value speed, experimentation and option capture more than error avoidance. A safety product can create strategic hesitation.

**Kill:** PROBE / review must not delay cheap reversible action whose execution generates equal or better information.

## A10 — Selective-support attack

Even a system that abstains or intervenes selectively can alter human behavior merely by signaling that support was or was not invoked.

**Kill:** routing must be behaviorally tested; 'silent pass' is not assumed neutral.

## A11 — First-use-value attack

Longitudinal history cannot justify first use because it does not exist yet.

**Kill:** the first consequential commitment must produce enough immediate value without relying on future compounding.

## A12 — Removal-test attack

If removal is noticed only because a UI disappeared, that is not indispensability.

**Pass only if:** the user recreates a decision capability, changes behavior, or incurs observable loss when the capability is absent.

# Adversarial outcome

## Standalone app: NOT ENTITLED TO EXIST

The current evidence does not justify a standalone destination application as the primary product.

Working hierarchy:

```text
USER NEED
  ↓
DECISION-SAFETY CAPABILITY
  ↓
BEST PLACEMENT / TRIGGER
  ↓
MINIMUM INTERACTION
  ↓
OPTIONAL APP SURFACE
```

The application becomes a **secondary inspector/configuration/history surface** unless a FIELD test shows that high-density manipulation itself creates unique decision value.

---

# New governing product question

Do not ask:

> How do we make the ProofMiner app indispensable?

Ask:

> **For which recurring commitment class is there a meaningful expected loss from acting without this capability, and what is the lowest-friction place to deliver it?**

---

# Wedge-before-app DOD

Before expanding the application, identify one commitment class that simultaneously has:

1. **material stakes** — wrong commitment costs meaningful time, money, reputation or opportunity;
2. **observable trigger** — the commitment reliably appears in one bounded work surface;
3. **bounded context** — enough decision-relevant context is available without broad surveillance;
4. **repeatability** — enough similar cycles exist to learn / justify integration;
5. **bounded signal horizon** — useful feedback returns soon enough to support learning;
6. **pre-state value** — capturing intent before outcome cannot be cheaply reconstructed later;
7. **action consequence** — support can plausibly cause PASS / MODIFY / PROBE;
8. **low intervention burden** — support does not cost more than the decision value it creates;
9. **strong-substitute advantage** — general AI + a simple template does not achieve equivalent value at similar effort;
10. **removal consequence** — removing the capability changes behavior or creates an observable loss.

If no commitment class passes, **kill the software-product hypothesis and retain the method as a service / protocol / agent capability**.

# Candidate wedges to falsify

These are hypotheses, not decisions:

### 1. Proposal / quote / client-scope commitment

Strengths: explicit artifact, price/scope/resource exposure, recurring event, clear accept/reject or negotiation signals.

Attack: much of the value may collapse into proposal review / sales enablement, a crowded category.

### 2. Paid campaign / launch commitment

Strengths: explicit spend, measurable outcome, repeated cycles.

Attack: strong analytics / experimentation substitutes already exist; strategic differentiation may be weak.

### 3. Hiring / vendor commitment

Strengths: high stakes, clear commitment.

Attack: low frequency, long feedback horizon, specialized evaluation requirements.

### 4. Broad professional-transition commitment

Strengths: highest conceptual fit with current doctrine.

Attack: triggers diffuse, outcomes slow/noisy, decisions heterogeneous, and app need weakest.

**Current adversarial ranking:** broad professional transition is the weakest software wedge despite being the richest conceptual domain.

# Next justified FIELD question

> **What is the narrowest recurring commitment for which a suitable user says, before outcome is known: “I would not want to make this class of commitment again without that check”?**

Until that class is found, do not invest further in making the destination app richer.
